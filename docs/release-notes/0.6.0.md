# PLC Data Collector 0.6.0 Release Notes

Release date: 2026-11-27

## Summary

PLC Data Collector 0.6.0 adds wired M-Bus (EN 13757-2 and EN 13757-3) as the
fourth real protocol, read-only. Heat, water and electricity meters are read
through a transparent TCP gateway or a serial level converter, by primary
address (0 to 250) or secondary address (the meter's identification number,
optionally with manufacturer, version and medium). A Tag selects one record of
one meter by its meaning (quantity, storage number, tariff, subunit, function
and qualifiers), never by its position in the telegram, and stores the value
in a unit it declares, converted exactly in decimal
([ADR 0005](../adr/0005-mbus-records-selected-by-meaning.md)). Billing totals
are stored as the number on the meter's display, and an optional `meter_id`
on each Tag notices a meter that was swapped or re-addressed.

Each Connection has one shared bus. Polling, "Test connection", "Read meter"
and "Scan bus" take turns on it, so a serial port is never opened twice and
scanning or adding Tags does not stop monitoring. "Scan bus" finds meters by
primary or secondary address in the background, with progress and Cancel.
"Read meter" reads one meter, lists its records with value and unit, and
creates a Tag for each ticked record. The Tag form, CSV paste and the JSON
import support M-Bus Tags. The demo stack includes an M-Bus simulator with
five meters. See [the M-Bus guide](../protocols/mbus.md).

**M-Bus support is not tested on real hardware.** There was no M-Bus
equipment for this release. The driver is verified against the simulator,
byte-level telegram fixtures, a serial pseudo-terminal and pyMeterBus as an
independent decoder in the tests. Before you bill from it, compare a total
digit by digit with the meter's display, and work through the guide's
hardware validation checklist. Please report any meter that behaves
differently.

## Breaking Changes

None.

## Upgrading from 0.5.0

- There is no migration; the schema stays at migration `0004`.
- The new runtime dependency is `pyserial` 3.5 (BSD-3-Clause, pure Python),
  for the serial transport. `pyMeterBus` 0.8.5 is a development dependency
  only, used by the tests as an independent decoder.
- **Uncertain readings may now carry `error_code` and `error_message`.** A
  `good` reading has neither; a `bad` reading has no value and an error code,
  as before; an `uncertain` reading has a value and may now have a code and a
  message that say why it is uncertain (for M-Bus, `mbus_meter_status` when
  the meter reports an error in its status byte). This applies to the
  `tag_readings` table and to `/api/v1` current values and history. The shape
  is unchanged, but a client that treats "has `error_code`" as "has no value"
  must check `quality` instead. Only M-Bus produces such readings in 0.6.0;
  OPC UA, Modbus and S7 behave as before.
- OPC UA, Modbus and S7 Connections and Tags are not affected.

## Rolling back to 0.5.0

There is no migration to undo, so 0.5.0 runs on the same database. M-Bus
Connections and Tags stay in it, but 0.5.0 has no driver for them. Archive
the M-Bus Connections before you roll back. Stored uncertain readings with an
error code stay in `tag_readings`.

## Compatibility

- Python: 3.12 or newer.
- Storage: PostgreSQL 17 (tested), SQLite as the fallback when no database URL
  is set.
- Real PLC and meter connectivity: OPC UA through `asyncua`; Modbus TCP
  through `pymodbus` 3.16.2; Siemens S7 through `python-snap7` 3.6.0; wired
  M-Bus through the project's own frame codec, over asyncio TCP or `pyserial`
  3.5. Modbus, S7 and M-Bus are read-only.
- The serial transport uses `pyserial`, which supports Linux, macOS and
  Windows. The serial tests run over a pseudo-terminal and are skipped on
  Windows.
- Deployment: Docker Compose demo stack, or an external process manager.

The release is validated by:

- full pytest suite, including tests against a real PostgreSQL,
- ruff linting,
- ruff formatting check,
- mypy strict type checking,
- third-party credits regeneration,
- a pyMeterBus cross-check of every fixture and simulator telegram,
- a Docker smoke test: simulators, collector and PostgreSQL started with
  `docker compose`, worker state checked through the API, good-quality readings
  confirmed to grow in `tag_readings`, Modbus, S7 and M-Bus smoke checks (their
  Tags reaching `tag_readings` with good quality), a Panel sign-in, an API key
  created in the Panel, and current values and history read from `/api/v1`.

Not part of the validation: a real M-Bus gateway, level converter or meter.

## Known Limitations

- M-Bus is not tested on real hardware (see the Summary).
- M-Bus is read-only: no setting of primary addresses, baud rates or the
  meter's clock. No wireless M-Bus, encrypted telegrams or OMS.
- Manufacturer-specific records, date and time records, plain-text and
  variable-length records, compact profiles and "selection for readout" are
  not read; Read meter shows them greyed with the reason.
- M-Bus is slow: keep "meters × 2.5 s" below the Tag Group interval.
  Battery-powered meters should not be read more often than once a minute;
  the Panel warns, but does not refuse.
- One collector process per bus, and one M-Bus Connection per gateway or
  serial port.
- Scan results and meter readings in the Panel are kept in memory and are
  lost on restart; Apply changes stops a running scan.
- S7 is not tested on real hardware either. S7 DBs with optimized block access
  cannot be read.
- Saving a large CSV paste, TIA import or Read meter selection writes one
  audit entry per Tag.
- The Panel has one admin password and no user accounts.
- The sign-in throttle (5 failed attempts in 5 minutes) counts per client IP
  address. Behind a reverse proxy every user arrives from the proxy's
  address, so all users share one limit, and failed attempts by one person
  lock out everyone for a few minutes.
- `/health/*`, `/api/runtime/*` and `/api/about` have no authentication.
- Every API key can read every Tag.
- Retention is global, one number of days for all Tags.
- A Poll Result that cannot enter a full Reading Queue within the timeout is
  dropped and counted as a failed cycle.
- Production PLC and meter interoperability must be validated against target
  devices before deployment.
